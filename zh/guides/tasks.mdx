## 任务是干什么的

任务是带上下文的工作项。每个任务知道：

- 你要做什么（PRD）
- 哪些文件相关
- 在哪个分支工作
- 当前状态

切换任务时，AI 的上下文也切换。不会搞混你在做哪个功能。

## 任务结构

任务在 `.trellis/tasks/`。每个任务是一个目录：

```
.trellis/tasks/01-31-user-auth-taosu/
├── task.json           # 元数据
├── prd.md              # 需求
├── implement.jsonl     # implement agent 的上下文
├── check.jsonl         # check agent 的上下文
├── research/           # 可持久化的规划调研
└── prototype/          # 用户界面任务：manifest、入口、预览和资源
```

目录名格式：`MM-DD-简短描述-负责人`。

## 创建任务

用任务脚本：

```bash
python3 .trellis/scripts/task.py create "user-auth" --assignee taosu
```

这会创建规划合同 v2 Task，初始层级为 `pending`。编辑 `prd.md` 后，用 `task.py set-planning-profile` 一次回答七项规划画像：全部为 `false` 推导为 `lightweight`；任一为 `true` 推导为 `complex`，并要求 `design.md` 与 `implement.md`。

用户界面任务必须显式启用原型合同：

```bash
python3 .trellis/scripts/task.py create "user-auth-ui" --assignee taosu --meta ui=true
```

完成 `prototype/manifest.json` 声明的入口和预览。PRD“用户可见结果”的管理块必须展示入口、预览、状态和摘要。`task.py prototype-status <task>` 同时报告批准状态与 PRD 引用是否一致。用户查看该版本后，`task.py approve-prototype <task> "<approval-evidence>"` 记录批准并同步 PRD 管理块。

### prd.md

写清产品变化，让读者不看技术设计也能理解。固定保持“目标 → 需求 → 用户可见结果”；需求只建立实际发生的变更类型分组，使用 `R1` / `R1.1` 编号；检查清单结果使用 `O1` 编号并映射需求。

```markdown
# 用户认证

## 目标

1. 用户可以用邮箱和密码注册、登录。

## 需求

### R1 新增

- **R1.1 创建账号**：用户可使用邮箱、密码和显示名注册。
- **R1.2 验证邮箱**：用户首次登录前必须验证邮箱。
- **R1.3 找回密码**：用户可通过邮件发起并完成密码重置。

### R2 保持不变

- **R2.1 会话策略**：现有会话过期行为保持不变。

## 用户可见结果

- [ ] **O1（R1.1、R1.2）** 新用户可以创建并验证账号，然后登录。
- [ ] **O2（R1.3）** 用户可以通过邮件找回账号访问权。
- [ ] **O3（R2.1）** 现有用户的会话时长保持不变。

## 不在范围内

- 社交登录（Google、GitHub）
- 两步验证
```

### 数据库变化的 design.md

当 `data_model_change=true` 时，`design.md` 必须包含数据模型章节、可执行的 `CREATE TABLE` / `ALTER TABLE` DDL、表与字段说明数据字典、约束/关系、迁移和回滚。每张变更表、DDL 中每个字段都要有业务备注：支持时使用原生 `COMMENT` / `COMMENT ON`；SQLite 一类方言使用 SQL 注释加数据字典。Mermaid `erDiagram` 保持可选。

### 上下文文件（JSONL）

告诉 agent 该读哪些文件：

```jsonl
{"file": ".trellis/spec/backend/index.md", "reason": "后端编码规范"}
{"file": ".trellis/spec/backend/api.md", "reason": "API 设计模式"}
{"file": "src/routes/auth.ts", "reason": "认证路由实现"}
{"file": "src/services/user.ts", "reason": "用户服务逻辑"}
```

不同 agent 可以有不同的上下文文件。按需编辑 `implement.jsonl`、`check.jsonl` 等。

## 开始做任务

`task.py start` 先校验 v2 规划画像以及 PRD 编号/映射。复杂 Task 还必须有 `design.md` 和 `implement.md`；交互变化必须提供文字标记且标红变化流程的 Mermaid 图；数据模型变化必须有 DDL 与表/字段备注。UI Task 随后还会校验原型文件、绑定摘要的批准和 PRD 管理块。任何失败都发生在状态、会话指针或生命周期 hook 改变之前。

设置当前任务：

```bash
python3 .trellis/scripts/task.py start 01-31-user-auth-taosu
```

Hooks 用这个来注入正确的上下文。现在开 Claude Code 会话时，它知道：

- 读这个任务的 PRD
- 加载 JSONL 文件里列的规范
- 在任务的分支工作

## 管理任务

列出所有任务：

```bash
python3 .trellis/scripts/task.py list
```

完成后清除当前任务：

```bash
python3 .trellis/scripts/task.py finish
```

归档已完成的任务：

```bash
python3 .trellis/scripts/task.py archive 01-31-user-auth-taosu
```

## 多个任务

可以同时有多个进行中的任务。但同一时间只有一个是「当前」的。切换：

```bash
python3 .trellis/scripts/task.py start other-task-id
```

## 任务工作流

典型流程：

1. 创建任务：`task.py create`
2. 编辑 `prd.md` 写需求
3. 用户界面任务完成 `prototype/`，检查 `task.py prototype-status`，并在用户查看后运行 `task.py approve-prototype`
4. 设置上下文文件（JSONL）
5. 设为当前：`task.py start`
6. 在 Claude Code 会话里工作
7. 归档：`task.py archive <id>`

任务系统把上下文组织好，让 AI 知道该关注什么。
